Kondex: Teaching Claude to use it

Tagged claude llm tools
Part 3 of 3 · kondex

  2. Searching the index
  3. Teaching Claude to use it

In my previous two posts, I covered how kondex builds its index and how you can query it. There's one part I haven't talked about yet, though: an index is not very useful if the LLM never thinks of using it. In this post, I'd like to go over how I got Claude Code to actually reach for kondex, which turned out to be surprisingly hard, and what I learned along the way.

If you look back at the architecture diagram in the first post, you'll notice a box labeled "kondex plugin", which contains a SessionStart hook and a skill. Let's see why both of them are there.

Starting with a skill

The obvious first move was a skill. A skill is cheap: a folder, a description, and a set of instructions that only get loaded when the model decides the description matches the task at hand. That last part is the catch — the description has to win against everything else competing for the model's attention.

.claude-plugin/plugin.json 
{
  "name": "kondex",
  "description": "Symbol and declaration lookup for large repos",
  "hooks": {
    "SessionStart": "./hooks/session_start.py"
  }
}

That worked, sometimes. On a fresh session with a clear question about a symbol, the skill fired. On anything else — a bug report, a refactor, a "why is this slow" — it did not. So I measured it.

Measuring it

If you cannot tell whether a change made the model reach for your tool more often, you are not iterating — you are guessing.

I wrote a small harness that replays a fixed set of prompts against a repository and records whether the index was consulted before the first file read. Crude, but enough to see movement. The hook below is what finally made the difference: it puts a short fragment into the session before the model has formed a plan.

hooks/session_start.py 
# Emit the fragment only when an index is present.
def main():
    index = Path(".kondex/index.db")
    if not index.exists():
        return
    print(FRAGMENT.format(count=count_symbols(index)))

Why a plugin?

A skill alone cannot run code at the start of a session, and a bare hook has nowhere to put instructions. Packaging both as a plugin means one install step, one version number, and one place to look when something misbehaves. It also means the fragment and the skill can refer to each other without me having to keep two copies of the same wording in sync.

The full source is on GitHub, and I'd be glad to hear from anyone who tries it on a repository larger than mine.
